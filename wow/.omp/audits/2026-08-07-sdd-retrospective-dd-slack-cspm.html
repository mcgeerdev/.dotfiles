04What you could have done differently

  1. State the timebox and the expiry rule up front. “Four hours to an approved spec. At four hours we cut scope, not add sections.”
  2. Approve a one-page slice statement before /grill-me. Three lines: v1 = critical and high CSM findings arrive in one shared Slack channel, routing managed in OpenTofu. Non-goals: playbooks, cases, tickets, acknowledgement, ownership, filtering, Yoma.
  3. Do not name a mechanism in the problem statement. “Slack notification with playbooks” committed to a delivery mechanism two hours before anyone knew the resource cannot carry a message.
  4. Ask for requirements, not requirements plus plan. The 08-06 prompt requested observability, rollout, rollback and secret handling inside a document called a specification.
  5. Pick the source of truth on day one, one directory, under Git.
  6. When 36 items arrived, the right instruction was “answer only what blocks PR1”, not “one at a time” — which turned a batching problem into a serialisation problem.
  7. Start PR1 while clarification continued. The spec’s own S1 stage proves it was independent.

Kept right: refusing to let the module be written during the interview; forcing one question at a time when overwhelmed; forcing the source-of-truth ruling; accepting RD23 when the plan surfaced a real deletion hazard; asking for a plain-English edition — correct instinct, wrong remedy.

05What the agent or workflow should have done

  1. Refuse to interview before a boundary exists. The right first move on a request naming an impossible capability is one question — visibility only, or visibility plus a work queue?
  2. Announce scope changes as scope changes. At 11:40Z the widening from vulnerability scanning to all of CSM arrived inside a message headed “Corrected”.
  3. Cap the review at five blocking items. Of 36, eight were labelled blocking; at most three blocked PR1.
  4. Write research to a research file from the first keystroke.
  5. Keep reversals out of the requirement document. The instinct behind §13 and §14 is right; the file is wrong.
  6. Stop asking what the repository or provider source can answer. FR-11/RD16 dissolved on evidence; the plan’s [D-9] was finally settled by building a credential-free fixture instead of asking — right move, made late.
  7. Never fork a document for readability. It created a second place decisions could live, and two immediately did.
  8. Do not reopen a closed gate for a plan-level guard. RD23 as an ADR plus a plan requirement costs nothing; as a spec amendment it produced a new section, requirement, criterion and risk row.

06Unavoidable work that must not be removed

This is security-sensitive routing whose failure mode is silence. Four properties of the surface make the analysis load-bearing rather than merely thorough:

  • Nothing validates the routing. selectors.query passes verbatim, unchecked by OpenTofu or Datadog, and rule_types has no element-level validation. A wrong value gives a clean plan, a clean apply, HTTP 200 and zero notifications indefinitely — indistinguishable from “no findings”. This alone justified deferring the filter out of v1.
  • Delivery can be silently absent. The Datadog app must be invited to the channel or every notification is dropped — with a live in-org precedent already delivering nowhere. account_name is ForceNew and unreadable by any provider resource; channel_name is not normalised, so a missing # gives a clean apply and a broken mapping.
  • Cut-over destroys the only proven path. Removing the email targets before Slack delivery is observed is total, silent loss. The staged S1–S4 delivery with a manual proof before cut-over is the correct structural answer.
  • The live object cannot be recreated. A version-8 rule edited eight times in a UI must be adopted by import; org-scoped duplicates fire with no error; and removing the resource block later plans a destroy, which prevent_destroy does not guard.

Budget it honestly: 45–60 minutes of read-only, parallelisable probing. Not three days. It felt like three days because it ran inside the decision loop instead of before it, and was written inside the specification instead of beside it.

09Implementing it with Spec Kit commands and gates

Spec Kit was considered on 08-06 at 13:49Z and declined — “I don’t have github’s SpecKit installed so I prefer this per prompt strategy”. The per-prompt strategy is what produced unbounded documents: every prompt was hand-written, so every prompt could ask for more. The toolkit replaces negotiable prose with fixed contracts. observed

uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z
specify init tofu-sdd --integration claude     # or --integration codex
specify preset search                          # security / compliance presets

The highest-value contract is /speckit.clarify. Its template mandates a maximum of five questions per session, asked exactly one at a time, each with a **Recommended:** option and a plain-language “why it matters” line; answers are written back into the spec under a dated ## Clarifications heading; anything over quota is flagged Deferred with a rationale. It also explicitly excludes “plan-level execution details” — exactly where FR-14, FR-15, RD7, RD9, RD11 and RD15 belonged.

Keeping security depth without inventing a framework

  • Use a preset, not a bespoke template. Presets exist to add mandatory security review gates to plans and enforce compliance-oriented spec formats. A didx-infra preset can require a silent-failure section in every plan and a positive delivery proof for every notification-path change.
  • Use hooks for the evidence probe. A mandatory hooks.before_clarify entry in .specify/extensions.yml runs the provider-schema and silent-failure probe: the analysis cannot be skipped, and cannot leak into the spec body.
  • Keep research and ADRs in the feature directory — specs/<n>-<slice>/research.md and …/decisions/*.md. The spec cites; it does not restate.
  • One repository, one copy, under Git.

The controls that would have stopped useful discovery from expanding the first release

None removes analysis; all relocate it.

  1. Approve the slice boundary before any interviewing — discovery then argues against a written boundary instead of expanding into a vacuum.
  2. A separate, timeboxed research artifact — findings land somewhere real without lengthening the document under review.
  3. A five-question clarify cap with an explicit Deferred list — 36 items becomes 5 questions and a 31-item backlog.
  4. One source of truth, one Git-tracked place, from minute one.
  5. Timebox expiry means split, not extend — a later discovery improves the next slice; it reopens the approved one only if it makes it wrong.
  6. Decision history in ADRs, not in the spec.
