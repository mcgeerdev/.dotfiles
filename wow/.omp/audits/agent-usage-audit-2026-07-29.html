What the data says

The advisor is the single largest controllable cost, and it is running with no project-specific configuration. It consumed $622.84 (26.3%) and produced 15,449 assistant turns against the primary agent's 11,133 — a ratio of 1.39 overall and a median of 1.33 per conversation. It issued 6,230 read/grep/glob calls to emit 1,669 advisory notes (3.7 lookups per note), and produced 1,297 byte-identical repeat calls. No WATCHDOG.md or WATCHDOG.yml exists at user or project level, so it reviews every turn against no stated priorities and with its default full-workspace remit.

Delegation, by contrast, is healthy. 97 subagents across 26 conversations cost $96.71 total, averaged 30 tool calls each, and recorded only 6 duplicate calls in 2,884. The reviewed subagent transcripts had narrow assignments and verified outcomes. No change is warranted here.

Model routing is not the lever. Only 11 conversations with ≤12 primary turns cost more than $1, totalling $14.32. Cheap-model substitution on short sessions cannot move a $2367.98 bill. One session (019f12aa) did 441 tool calls and 378 turns on deepseek-v4-pro for $3.70, which is the real routing signal: reasoning level and advisor cadence dominate, not session length.

465 error bodies (2.1% of tool calls) are addressable today — 340 from agent habits the harness can prevent (266 blocked shell forms, 48 Python-kernel calls, 26 malformed internal-URI and tool-argument errors) plus 125 primary results voided by pending advisories. A further 284 speculative path probes are a measured symptom with an unestablished cause, 86 voided results come from your own mid-turn messages and peer coordination, and 331 are legitimate signal or safety controls working as designed. §5 splits all 1,166 bodies across those four buckets.

Advisor — what the runtime actually guarantees

Per omp://advisor-watchdog.md, and correcting a claim in an earlier draft of this report:

  • The advisor does retain context within a session. “The advisor's live context is in-memory and append-only; it is retained while the session runs.” It receives only the new transcript delta at each primary turn end, not a replay of the whole conversation. Repeated lookups are therefore not explained by an absence of memory.
  • Its context can be rebuilt mid-session. Before each advisor prompt the runtime may promote to a larger model, compact the advisor's own history, or re-prime from the current bounded primary transcript; re-prime is a reset that clears the advisor's private transcript and its dedupe ring.
  • It does not share the primary agent's file state. The advisor runs its own ToolSession and “does not share the primary agent's file snapshots, seen-lines tracking, conflict state, summary cache”. This explains duplication between advisor and primary, but not duplication within the advisor.
  • What is missing is priorities and remit, not memory. WATCHDOG.md supplies review priorities and WATCHDOG.yml declares each advisor's model and tool grant. Neither file exists, so the advisor runs with the default read-only pool and no stated focus.

hypothesis Why the repeat lookups happen is not established. Candidate causes: re-prime/compaction cycles discarding earlier findings; an unbounded review remit that re-walks the tree each cycle; or the model simply re-issuing lookups it already has in context. These are distinguishable — /advisor status reports context usage, and re-prime events are observable in the advisor's own trace. Test: take one long session, correlate duplicate-signature bursts against advisor context-maintenance events. Until that is done, treat the 1,297 duplicates as a measured symptom with an unknown cause.

8. Skills and configuration recommendations

Ordered by expected impact. No configuration or skill file was modified by this audit.

R1. Give the advisor a written remit via WATCHDOG.md / WATCHDOG.yml implemented 2026-07-29 high confidence

The advisor currently reviews every turn against no stated priorities, using the default full read-only workspace pool. A priorities file narrows what it considers in scope; a roster file lets you pin its model and tool grant per project. This is a scope fix, not a fix for the duplicate lookups — those have an unestablished cause (§4).

EvidenceNo WATCHDOG.md or WATCHDOG.yml exists at user or project level (verified by filesystem check). Advisor issued 6,230 lookups for 1,669 notes with 251 path-not-found errors.
AffectedAll 137 OMP conversations with an advisor; $622.84 of observed spend.
Smallest changeDone: canonical roster at ~/.dotfiles/nvim/.omp/WATCHDOG.yaml, symlinked to ~/.omp/agent/WATCHDOG.yaml via .omp/agent/WATCHDOG.yaml → ../WATCHDOG.yaml, so one file serves every project. One advisor entry (Doctrine), no model: override (inherits modelRoles.advisor, so no cost change), no tools: override (default read-only pool). The six review priorities and a scope-discipline block live inside advisors[].instructions rather than top-level instructions:, because entries sharing a slug are replaced by the more specific file while top-level instructions are concatenated across every discovered file — this path is also a project-level roster for ~/.dotfiles/nvim, so the entry form yields exactly one copy of the remit everywhere. Verified live: a print-mode session produced __advisor.doctrine.jsonl, proving the roster was discovered and passed OMP's own schema validation (a rejected file is logged, skipped, and would have produced plain __advisor.jsonl).
Expected benefitA narrower review remit and advice aligned to your doctrine. Any reduction in lookups per note is a hypothesis to be measured, not a promise — the mechanism linking remit to lookup volume is untested.
Verify byRe-run this audit after a week and compare advisor lookups per advise note (currently 3.7), path-not-found errors (currently 251), and advisor cost share (currently 26.3%). If lookups per note do not move, the remit was not the binding constraint — run the §4 re-prime correlation test next.

10. Methodology and privacy notes

  • Collection: collect-usage.mjs parsed 633 transcript files and included 395 modified since 2026-06-29. All counts, token totals, and costs come from that deterministic pass or from recomputation over its per-session records — no figure was estimated by a model.
  • Grouping: OMP files were grouped into 154 conversations by session directory (primary file, __advisor.jsonl, and named subagent files), which is how per-conversation advisor and subagent shares were derived.
  • Qualitative review: 10 transcripts read in full, chosen from the collector’s cost, duplicate, error, and fan-out candidate lists plus two low-cost controls. Findings paraphrased.
  • Error classification: every error-bearing session was re-scanned and all 1166 error bodies bucketed by pattern into 15 classes that sum to the total, then split again by who can fix them (§5). Three defects in earlier drafts are corrected here: 207 bodies sat in an undisclosed remainder; shell-command failures were understated as 8 when the true figure is 133; and a claimed 917 “preventable” bodies both double-counted legitimate discovery and user-initiated interruptions and listed addends corresponding to no class. The preventable figure is 465.
  • Runtime claims verified against source: advisor context, delta rendering, reset triggers, and tool isolation were checked in omp://advisor-watchdog.md; configuration keys against omp://settings.md. An earlier draft asserted the advisor has “no memory” between review cycles. That is false — its context is in-memory and append-only, retained while the session runs — and the claim has been removed along with the recommendation that depended on it.
  • Evidence discipline: observed counts are stated plainly; mechanisms that are not measured are labelled hypothesis and carry a stated test (§4, R1, R9). No dollar savings are claimed anywhere.
  • Privacy: transcripts were read locally and never transmitted. This report contains no prompt text, tool arguments, file contents, secrets, or tokens. Tool arguments were hashed for duplicate detection. Session identifiers are abbreviated to 8 characters. The companion agent-usage-summary.json is written with mode 0600 and contains metadata only.
  • Artifacts: agent-usage-audit-2026-07-29.html and agent-usage-summary.json in ~/.dotfiles/nvim/.omp/audits. The JSON is mode 0600 and holds session metadata including absolute project paths — if this directory is inside a published dotfiles repository, exclude it from version control.
